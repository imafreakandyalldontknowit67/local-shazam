Olaf runtime, not a Node/web application. There is no root `package.json`
workflow. Recorded completed checks below are distinct from future procedures
and open gates. This document authorizes no build, CI dispatch, remote mutation,
publication, screenshot capture or deletion.

## 2. Future independent artifact checks

- [ ] Require separate build/test/package/verify results for each intended output.
  Use only the exact dataset-free allowlist: ten Rust selections, three Olaf
  regressions and app help/version plus Olaf help. Record execution mode; x86
  target tests on x64 remain WOW64. No unrestricted tests, music, personal
  databases, benchmarks or indexing are part of these gates.
- [ ] Retain a pre-upload ledger of filenames, byte sizes and SHA-256 values,
  including the checksum file and executable payload hashes. Check the matching
  full commit, source inventory, per-target identical `BUILD-PROVENANCE.json`,
  source/payload correspondence, notices, architecture/modes and gate records.
- [ ] Check actual binaries, source members, provenance and archive metadata
  against [Build privacy](BUILD_PRIVACY.md), including
  `compiler-paths-and-artifacts-v1` and native response-file handling. Preserve
  sanitized feature/link/SDK evidence and its gaps. Do not infer privacy from
  hashes or patch old binaries; keep source-only hygiene separate.
- [ ] After any separately authorized upload, download **actual asset bytes** to
  a separate location, recompute hashes/sizes and compare every intended asset
  with the pre-upload ledger, including the combined checksum file itself.
  Account for missing/extra assets; API digests and upload success are not enough.
- [ ] Independently verify the downloaded target trios in **separate per-target
  directories**. Each contains exactly three archives and a `SHA256SUMS.txt`
  with only that target's three entries. Retain original combined checksum bytes
  unchanged elsewhere; do not pass all seven release assets to one verifier.
  Keep screenshots and evidence outside the verification directories.
- [ ] Record actual final release state and inventory against the authorized
  plan. Uploads are not transactional; stop and preserve evidence on mismatch.
  No release/tag/visibility change is authorized by this checklist.

The verifier also supports complete historical `local-shazam-COMMIT12-TARGET`
sets with `SHA256SUMS` and applicable legacy native provenance. It rejects mixed
formats, ambiguous checksum files and incomplete sets. Historical-format support
is not a privacy exemption: missing compiler-policy records require a rebuild,
not altered old evidence. Checksums establish correspondence, not publisher
authentication or bit-for-bit reproducibility.

## 4. Workflow boundaries, cleanup and open gates

The manual [private-draft workflow](../.github/workflows/private-draft.yml)
creates **new private draft prereleases only**, with `create_draft=false` by
default. Creation requires an existing reviewed tag at the exact selected
commit, typed confirmation, all **five** target gates and aggregate verification.
It refuses existing releases and requests `draft=true`, `prerelease=true`,
`make_latest=false`. It has no existing-release update or publish/promote path.
These restrictions do not contradict the separately recorded Windows-only private
Latest release and are not instructions to demote/recreate it. Live environment
protections/denial paths are not established by static workflow inspection.

- [ ] Clean-host feasibility and minimum OS/runtime behavior: parent-owned, open.
  Recipients need the complete matching package, external FFmpeg **and** FFprobe
  on PATH and architecture-appropriate Microsoft runtime components from official
  installers; no Python. See [Quickstart](QUICKSTART.md).
- [ ] Native 32-bit Windows OS validation, audio smoke/accuracy, stability,
  signing and reproducibility remain unestablished. The x86 **512 MiB database
  mapping limit is not a total-RAM promise**; use a small folder/two workers,
  and a fresh index/reindex when switching architecture.
- [ ] Historical privacy/publication-surface review remains parent-owned and open.
- [ ] Retention decisions, exact-directory approval and any cleanup belong to the
  parent/maintainer under [Build cleanup](BUILD_CLEANUP.md). Download verification
  is necessary evidence, not deletion authorization; retain recovery copies.
- [ ] **Licensing review and public-release approval remain OPEN.** Preserve
  [release review](../licenses/RELEASE_REVIEW.md) and the bounded
  [Windows distribution review](../licenses/WINDOWS_DISTRIBUTION.md); successful
  private packaging does not close legal, source-offer or public-launch gates.
