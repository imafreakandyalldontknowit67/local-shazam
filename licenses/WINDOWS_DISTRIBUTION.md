# Windows-only distribution review ? 2026-11-01

## Scope and decision

The owner authorized packaging and publishing the updated Windows build as Latest
**inside the existing private repository**, with matching sources and notices.
No repository visibility change, public launch, music upload or hosted recognition
service is authorized. This is a factual engineering review, not legal advice or
a certification of every possible deployment. Prior review documents remain
historical records; macOS and Linux are excluded from this release.

## Selected dependencies and attribution

- Locked Cargo metadata resolved for `x86_64-pc-windows-msvc` contains the app
  and 72 dependencies. The sanitized package/version/license/feature list is
  [retained here](review/windows-selected-dependencies.json). It includes build
  dependencies and is not an exact linker map.
- None of the seven Apple-family crates or `sqlite-wasm-rs` is selected in this
  target graph. Their implementation sources are not bundled. Their unresolved
  reviews remain relevant to other targets, not evidence of a Windows dependency.
- Existing registry notices, upstream credits, Olaf modifications, ordered patches,
  AGPL text and embedded-component notices are retained. No copyright holder or
  missing grant is invented and no component is relabeled as MIT.
- The Rust 1.99.0 installation's `COPYRIGHT-library.html` and accompanying license
  texts are included under `runtime/rust-1.99.0`. This intentionally broad
  notice inventory is not a claim all listed components were linked.
- The installed Zig 0.16.0 root license and mingw-w64 COPYING were compared with
  the retained notices after newline normalization. Olaf's Windows provider uses
  `x86_64-windows-gnu`; the Rust app uses the MSVC target. No compiler executable,
  Windows SDK, Microsoft runtime installer or Microsoft runtime DLL is bundled.
- FFmpeg and FFprobe remain external prerequisites. Microsoft runtime components
  required on a recipient machine should come from Microsoft's official installer,
  not copies of the development machine's DLLs. See [Microsoft's redistribution
  guidance](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170).

## Corresponding source and recipient rights

Publish the exact app-source and Olaf-source archives **alongside the binary ZIP**
with equivalent repository access and no additional charge. Do not substitute
GitHub's autogenerated source archive, a private fork link or a moving branch.
The verifier checks corresponding source inventories, vendored runtime components,
build scripts, notices, configuration and ordered patch series against the binary
provenance. Preserve both source archives when redistributing the package.

This delivery follows the designated-place source-access mechanism in
[AGPL section 6(d)](https://www.gnu.org/licenses/agpl-3.0.html). Original application
code remains MIT; modified Olaf remains AGPL-3.0-or-later. The subprocess boundary
is not treated as an AGPL exemption. No proprietary-only terms, NDA or additional
restriction on recipients' license rights is imposed by this release. Repository
access controls are not a replacement for recipients' source access or rights.

The inspected application invokes local Olaf store/query CLI commands and verifies
local audio; it does not deploy the runtime REST service. This does not resolve
obligations for a future hosted service: review section 13 before operating one.
This portable software release does not transfer a locked hardware device or
require a signing key to install a modified runtime. General combined-work,
patent and future deployment questions remain subject to qualified legal review;
this document does not declare a subprocess-based exemption or certify legal safety.

## Verification and limitations

Before promotion, require fresh Windows build/test/package verification, uploaded
archive download/hash comparison and explicit private-visibility recheck. Keep the
historical multi-platform draft separate; do not present its old Linux/macOS builds
as updated or sanitized. Native packaging tests do not establish snippet accuracy,
minimum supported OS, a clean-host install, signing or hardware stability.

The owner requested a private Windows release, not a public readiness certification.
A future public launch still needs its own publication-surface and deployment review.
